## Step 7
- **Step / commit:** `Fix application error: return 404 instead of crashing on ids larger than SQLite can store`
- **Prompt:** Proceed to Step 7 and pick the error I see. (The real error was gap (a) from the Step 6 probe: HTTP 500 on a huge id.)
- **AI response:** Used systematic debugging. Phase 1: reproduced with the full stack trace (router `return_equipment` -> service `return_borrow` -> `db.get` -> `OverflowError: Python int too large to convert to SQLite INTEGER`) and measured the exact boundary (2**63-1 gives 404, 2**63 gives 500; same for `equipment_id` in a borrow). Root cause: ids were plain unbounded Python ints, but SQLite stores ids as signed 64-bit; an out-of-range value passed validation, reached the driver, and the unhandled error became a 500. Wrote the failing tests first (4 failures `500 == 404`), then realised the negative side overflows too and added those cases (8 failures total). Fix: `get_by_id()` in `database.py` returns None ("not found") for an out-of-range id without querying; `borrow_service.py` uses it in both places.
- **Evaluation:** (draft) 132 tests pass (120 + 12 new). Re-ran the original failing requests against the live server: all 404 with the normal "not found" messages, zero `OverflowError` in the log, a real record still works. Chose 404 (not 422) because section 9 says a non-existent id is 404 and ids 0, -1 and 999 already behave that way. Alternatives rejected: catching OverflowError globally (hides the cause) and bounding the ids with a 422 (a second behaviour for the same idea). Known gaps still OPEN (not part of this fix): JSON `true` accepted as a number, control characters in names, "Dell  Latitude" double-space near-duplicates, `?category=` / `?status=` with an unknown value return 200 [] (plan says 422), very long error text for a 31-digit quantity.
